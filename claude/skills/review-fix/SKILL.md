# review-fix スキル

レビュー指摘を自動でIssue登録し、並列サブエージェントで修正する。

## コマンド

| コマンド | 用途 |
|---------|------|
| `/review-fix` | フルフロー: レビュー→Issue登録→並列修正→コミット |
| `/review-fix --plan` | レビュー→Issue登録→修正計画の提示（実装はしない） |
| `/review-fix --high` | High以上のみ修正（Medium/Lowは登録のみ） |
| `/review-fix --all` | 全重大度を修正対象にする |
| `/review-fix --issues` | Issue登録のみ（修正しない） |
| `/review-fix --issues --fix` | 既存の未クローズIssueから修正を実行 |
| `/review-fix --scope <パス>` | 指定パス配下のみ対象 |
| `/review-fix --dry-run` | 全フローをシミュレート（変更なし） |

デフォルト動作: `--high` 相当（High以上を修正、Medium/Lowは登録のみ）

## フロー

### Phase 1: レビュー実行
1. `/review` スキルを呼び出してフルレビューを実行
2. `docs/review-report.md` の生成を待つ

### Phase 2: レポート解析
1. `docs/review-report.md` を読み込み
2. YAMLフロントマターから統計情報を抽出
3. 各指摘をパース: ID, 重大度, カテゴリ, ファイル:行, 問題, 修正案

### Phase 3: Issue登録
1. 各指摘をGitHub Issueとして登録
2. ラベル付与: `priority:critical`, `priority:high`, `priority:medium`, `priority:low`
3. カテゴリラベル: `security`, `performance`, `testing`, `docs`, `enhancement`
4. 登録結果をユーザーに報告

### Phase 4: 修正計画
1. **安全性ポリシー判定**: 各指摘を以下のマトリクスで分類
   - AUTO（自動修正）: High×small, Medium×small
   - CONFIRM（確認後修正）: Critical×any, High×medium/large
   - SKIP（登録のみ）: Large工数, アーキテクチャ変更
2. **ファイル競合マップ作成**: 修正対象ファイルの重複を検出し、競合しないグループに分割
3. 計画をユーザーに提示し承認を得る

### Phase 5: 並列修正
1. 承認された計画に基づき、3〜4個のサブエージェント（Task tool）を並列起動
2. 各エージェントに委譲する情報:
   - 修正対象のIssue一覧（ID, ファイル, 問題, 修正案）
   - 対象ファイルの一覧
   - テストコマンド
3. 各エージェントは修正後にテストを実行して結果を報告

### Phase 6: 統合・コミット
1. 全エージェントの完了を待つ
2. 全テスト実行（バックエンド + モバイル）
3. `git diff` で変更内容を確認
4. コミットメッセージを作成（修正したIssue番号を含む）
5. ユーザーの承認を得てコミット
6. 修正済みIssueをクローズ

## 安全性ポリシー

### 自動修正可能（AUTO）
- 単一ファイル、10行以内の変更
- テスト追加・修正
- ドキュメント更新
- import修正、型エラー修正
- 依存関係の脆弱性修正（patch update）

### 確認必要（CONFIRM）
- Critical重大度の全指摘
- 2ファイル以上の変更
- ビジネスロジックの修正
- 設定ファイルの変更
- セキュリティ関連の修正

### スキップ（SKIP）
- large工数の指摘
- アーキテクチャ変更を伴う指摘
- 破壊的変更の可能性がある指摘
- 外部サービス連携の変更

## ファイル競合回避ルール

並列サブエージェントが同一ファイルを同時に変更しないよう、以下のルールを適用:

1. 各指摘の対象ファイルを抽出
2. ファイルが重複する指摘は同一グループに配置
3. グループ間でファイルが重複しないことを検証
4. 推移的依存も考慮（A→B, B→Cの場合、A,B,Cは同一グループ）

## エラーハンドリング

| 状況 | 動作 |
|------|------|
| レビューで指摘0件 | 「問題なし」と報告して終了 |
| Issue登録失敗 | 失敗したIssueをスキップし、成功分で続行 |
| サブエージェントエラー | 失敗グループを報告、成功分のみコミット |
| テスト失敗 | コミットせず、失敗内容を報告 |
| ファイル競合検出 | グループを再分割して直列実行 |

## 注意事項

- コミット前に必ず全テストをパスさせる
- 1コミットに全修正をまとめる（グループ別コミットはしない）
- `--dry-run` では一切のファイル変更・Issue登録を行わない
- サブエージェントは最大4個まで（APIレート制限考慮）
- 修正中に新たな問題を発見した場合、報告のみで追加修正はしない
